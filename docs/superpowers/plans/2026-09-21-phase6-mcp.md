# Phase 6: MCP stdio Integration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Connect configured MCP servers over stdio and expose their tools through the Phase 5 `ToolRegistry` contract.

**Architecture:** `McpManager` in `packages/mcp` owns one official MCP SDK stdio client session per configured server. It adapts discovered MCP tools to Phase 5 `Tool` objects named `<serverId>__<toolName>`, carrying internal MCP source metadata; all execution continues through `ToolRegistry`. The operator explicitly trusts every tool exposed by a server they add to `config/mcp.json`, so those tools are marked `safe`. `apps/api` loads and validates the config, starts servers independently, exposes redacted status at `GET /api/mcp`, and closes all sessions on shutdown. `agent-core` remains MCP-agnostic.

**Tech Stack:** Node.js >=24, TypeScript strict, official `@modelcontextprotocol/sdk` 1.30.0 (exact pin), `jsonc-parser` 3.3.1 in `apps/api` (exact pin; use strict JSON parse settings and inspect object-property AST nodes for duplicate keys), npm workspaces, Vitest.

**Spec:** `docs/superpowers/specs/2026-09-23-phase6-mcp-design.md`; product requirements: `PROMT.md` §§3, 8–10, 15, 17–20, 24.

## Global Constraints

- MCP transport is stdio only; do not add MCP UI, model tool loop, tool persistence, or HTTP tool execution.
- A configured server failure must not prevent API startup or healthy server availability.
- Only registered tools execute, through `ToolRegistry`; its exact-name and `safe` checks remain authoritative.
- Never expose or log environment values, secret values, or command environment in errors or HTTP responses.
- Pass only explicitly configured `env` overrides to the MCP stdio SDK; retain its safe inherited defaults, and never forward all parent process variables.
- Expand only whole-value `${ENV_NAME}` references in `args` and `env`; `command` remains a literal config value.
- A missing `config/mcp.json` means an empty server map; malformed existing JSON fails with a sanitized actionable error.
- Keep `packages/agent-core` provider/storage/tool/MCP implementation agnostic.
- Each server ID and tool name must be deterministic; do not silently overwrite duplicate JSON keys or registry names.
- Tests mock MCP SDK/process I/O; no real MCP server or external model API is required.
- Preserve unrelated working-tree changes. Do not start API/web dev or watch processes for verification.

## MCP Package Contract

Export these public types from `@agenter/mcp`:

```ts
export interface McpServerConfig {
  command: string;
  args?: string[];
  env?: Record<string, string>;
}

export interface McpServerStatus {
  id: string;
  status: "ready" | "error";
}

export class McpManager {
  constructor(registry: import("@agenter/tools").ToolRegistry);
  start(config: Record<string, McpServerConfig>): Promise<void>;
  listTools(): Array<import("@agenter/tools").Tool & {
    source: { kind: "mcp"; serverId: string };
  }>;
  getServerStatus(): McpServerStatus[];
  stop(): Promise<void>;
}
```

`apps/api/src/mcpConfig.ts` returns `Record<string, McpServerConfig>` and
imports this type from `@agenter/mcp`; the manager receives the same shared
registry instance used by the API.

## Acceptance Criteria

- Configured stdio MCP servers start, expose tools through the common `ToolRegistry`, and stop cleanly.
- Server failures are isolated; API startup and healthy server tools remain available.
- `GET /api/mcp` reveals status and tool metadata only, never process configuration or secrets.
- Duplicate config keys and invalid configuration fail safely and actionably.
- No `agent-core` MCP/provider-specific branch, model tool loop, MCP UI, or non-stdio transport is introduced.
- Root typecheck, lint (no new errors), full tests, and clean diff checks complete with recorded evidence.
