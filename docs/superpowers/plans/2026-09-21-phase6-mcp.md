# Phase 6: MCP stdio Integration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Connect configured MCP servers over stdio and expose their tools through the Phase 5 `ToolRegistry` contract.

**Architecture:** `McpManager` lives in `packages/mcp` and owns process/session lifecycle. It uses the official MCP SDK, converts discovered MCP tools into `Tool` adapters, and isolates one server's failure from other servers and API startup. The API loads `config/mcp.json`; `agent-core` sees only normalized tool interfaces.

**Tech Stack:** Node.js >=24, TypeScript strict, official MCP SDK pinned exactly, npm workspaces, Vitest.

**Spec:** `PROMT.md` §§3, 8, 9, 10, 15, 17, 18, 19, 20, 24 (Phase 6).

## Configuration

```json
{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "./workspace"]
    }
  }
}
```

Environment expansion is limited to documented non-secret command arguments;
API keys must remain environment-backed and must never be logged.

## Interfaces

```ts
export interface McpServerConfig {
  command: string;
  args?: string[];
  env?: Record<string, string>;
}

export interface McpManager {
  start(config: Record<string, McpServerConfig>): Promise<void>;
  listTools(): Array<Tool & { source: { kind: "mcp"; serverId: string } }>;
  stop(): Promise<void>;
  getServerStatus(): Array<{ id: string; status: "ready" | "error" }>;
}
```

The normalized MCP tool carries its source server in the optional Phase 5
`Tool.source` metadata; the source is not part of the provider-facing
`Tool.name` and cannot be supplied by model arguments. `McpManager` registers
the same metadata-bearing object in `ToolRegistry`, so it survives lookup and
execution. Configuration is parsed from raw JSON text with duplicate-key
detection before it is converted to `Record<string, McpServerConfig>`; this
prevents silent replacement of one server definition by another.

## Tasks

- [ ] **Task 1:** Add failing configuration tests for valid stdio entries, malformed entries,
   duplicate raw JSON keys, and secret-safe error messages.
- [ ] **Task 2:** Add the exact-pinned official SDK dependency and implement one session per
   configured server with explicit `start`, `listTools`, and `stop` lifecycle.
- [ ] **Task 3:** Convert MCP tool schemas/results into Phase 5 `Tool` adapters. Preserve the
   originating server id in internal metadata.
- [ ] **Task 4:** Add failure-isolation tests: one process failing must leave healthy servers
   available and must not prevent API bootstrap.
- [ ] **Task 5:** Add `GET /api/mcp` status output without exposing command secrets, and wire
   bootstrap shutdown handling for MCP sessions.
- [ ] **Task 6:** Run mocked SDK/process tests and all root checks. No real MCP server is
   required for the test suite.

## Acceptance criteria

- stdio servers start, advertise tools, execute through the common registry,
  and stop cleanly.
- A failed server is reported and isolated; healthy servers remain usable.
- `GET /api/mcp` exposes status and tool metadata but no secrets.
- No AgentRuntime provider-specific or MCP-specific branching is introduced.
