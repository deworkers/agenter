# План доработок UI/UX Agenter

Дата: 2026-10-02. Статус: **утверждён пользователем; этапы 1–7 реализованы, браузерная проверка этапов 3–7 ограничена**.

Основание: аудит приложения в Chrome на `http://127.0.0.1:5173/`, проверка текущего кода и требований `PROMT.md`. План продолжает утверждённый объём из [settings-context-mobile](2026-09-28-settings-context-mobile.md), учитывает [Phase 8](2026-09-21-phase8-ui.md) и выделяет отдельный объём надёжности относительно [Phase 9](2026-09-21-phase9-reliability.md). Наличие этого документа не означает утверждения новых требований или завершения Phase 8/9.

## Цель и границы

Сделать историю чатов основным содержимым боковой панели, прояснить выбор навыков и инструментов, показывать состояние генерации и объяснять ошибки. Сохранить существующие настройки, ограничения инструментов, хранение истории и разделение ответственности пакетов.

Работы выполнять последовательно, отдельными проверяемыми изменениями. Пользователь поручил реализовать план по пунктам; это согласование охватывает изменения поведения, описанные в этапах 1–7. Этапы 1–3 дают основные улучшения панели. Не включать оптимизацию локального сервера модели, несколько одновременных запусков, полный набор Phase 9 или новые MCP-интеграции.

При аудите файлы приложения не менялись. Для функциональных проверок были созданы три тестовых диалога. В рабочей копии уже есть изменения пользователя; при реализации нужно учитывать их актуальное состояние и сохранять их.

## Что уже работает и что проверено

- Ответ через `api-fast`, продолжение диалога с сохранением контекста и отмена генерации.
- Навыки редактирования, веб-поиска, Context7 и выдачи полного кода. Проверены реальные вызовы поиска, `fetch` и двух инструментов Context7.
- Создание и предпросмотр HTML/Markdown, восстановление ответов, файлов и активности инструментов после перезагрузки.
- Локальные команды `/help`, `/model`, `/compact`. Сжатие сохраняет исходные сообщения и позволяет продолжить диалог.
- Черновики и выбор возможностей уже сохраняются по чатам. `useMcp` уже разделяет ручной и автоматический выбор серверов; повторно строить эти механизмы не нужно.

Локальная модель при одном запуске не выдала текст за 52,5 секунды до отмены. Это наблюдение о задержке, а не доказательство неисправности провайдера. Скачивание файла осталось непроверенным в реальном браузере из-за ограничения автоматизации; существующие тесты механизма Blob не заменяют эту проверку. Остальные навыки/MCP и физическая мобильная клавиатура требуют отдельной проверки.

## Этап 1. Боковая панель и поиск истории — P1 — выполнен

**Проблема.** На проверенном desktop-экране история занимала около 152 px, а блок инструментов — 342 px. После сворачивания инструментов история получала около 452 px. Два прокручиваемых списка конкурируют за место, повторяющиеся подписи «Workspace»/«Чат» увеличивают шум.

**Изменения.**

- Верх панели: заметная кнопка «Новый чат» и поле «Поиск чатов».
- История занимает оставшуюся высоту. Поиск фильтрует загруженные названия; пустой результат показывает понятное сообщение и действие очистки. Не обещать поиск по тексту сообщений без отдельного backend-объёма.
- Группировать историю по времени последней активности: «Сегодня», «Вчера», «Ранее». Активный чат различим без наведения; длинные названия сокращаются с доступным полным названием.
- Меню строки содержит переименование и удаление; действия доступны с клавиатуры и на touch-экране. Переименование подключить на этапе 2.
- Внизу — сворачиваемый блок «Возможности» с кратким состоянием выбора и «Настройки». На первом открытии блок свёрнут; явный выбор пользователя сохраняется как локальная UI-настройка.
- Убрать дублирующие заголовки. Редактирование/создание ресурсов оставить в настройках, переключение доступных возможностей — в панели.

**Основные файлы:** `apps/web/src/components/Sidebar.vue`, `CapabilitySwitches.vue`, `apps/web/src/style.css`, подключение в `App.vue`.

**Приёмка.** При свёрнутых возможностях история занимает большую часть панели; при раскрытии длинного каталога история остаётся доступной. Проверить 0, 1 и 100 чатов, длинные названия, поиск и очистку, прокрутку и возврат в активный чат. На ширинах 320/390/768 px нет горизонтального скролла, drawer открывается и закрывается доступным действием. Поведение поиска покрыть небольшими тестами фильтрации; геометрию проверить в браузере.

## Этап 2. Стабильные названия и переименование — P1 — выполнен

**Проблема.** Каждое сообщение меняет название чата; вставленный текст часто превращает его в «Из буфера.txt». Это происходит и во frontend, и в SQL-чтении, которое берёт последнее сообщение пользователя вместо сохранённого названия. Исправление только панели не обеспечит сохранность названий.

**Изменения.**

- Новый чат получает «Новый чат». Первое содержательное сообщение устанавливает короткое название один раз; последующие сообщения меняют порядок по активности, сохраняя название.
- При первом запросе только с вложением использовать содержательное имя файла; для общего имени «Из буфера.txt» — нейтральное название без подстановки содержимого файла в инструкцию модели. Не добавлять отдельный LLM-запрос для заголовка.
- Добавить переименование через меню строки, минимальный `PATCH /api/chats/:id` и метод storage-интерфейса. Валидировать непустое название и ограниченную длину; при ошибке сохранять введённый текст и корректно откатывать отображение.
- Сделать сохранённое название авторитетным при чтении. Для старой БД сохранить текущие отображаемые названия при переходе, если раньше в поле было только значение по умолчанию. Существующие содержательные/пользовательские названия не перезаписывать. Правило и минимальную миграцию зафиксировать тестами до реализации.

**Основные файлы:** `useChats.ts`, API `client.ts`/`types.ts`, `routes/chats.ts`, `services/ChatService.ts`, `packages/agent-core/src/types.ts`, `packages/storage/src/SqliteChatStorage.ts` и миграции при необходимости. SQL остаётся в storage.

**Приёмка.** Второе сообщение, ошибка, отмена, `/compact` и перезагрузка не меняют название. Ручное название сохраняется даже до первого сообщения. Старая БД открывается без потери истории и названий. Тесты storage/API/composable проверяют автоматическое именование, ручное переименование, валидацию и отказ сервера.

## Этап 3. Прозрачный выбор навыков/MCP и доступность — P1 — реализован

**Проблема.** Навыки показаны переключателями, хотя выбрать можно только один. Счётчик «Инструменты 2» считает навык и сервер, а не доступные функции. После выключения навыка автоматически выбранный MCP остаётся включённым. Настройки открываются без перевода фокуса в диалог, Tab может попасть в фон. Мелкие подсказки имеют низкий контраст.

**Изменения.**

- Навыки оформить как одиночный выбор с вариантом «Без навыка»; серверы MCP оставить множественным выбором.
- Раздельно показывать выбранный навык, число подключённых серверов и число разрешённых функций. Для функций считать доступный набор после статуса сервера и allowlist, а не все обнаруженные инструменты. Если каталог не содержит достаточных данных, расширить безопасные метаданные `GET /api/mcp`; правила допуска остаются на сервере.
- Использовать существующие `manualServerIds`/`automaticServerIds` для пометок «Выбран вручную» и «Подключён навыком». Отключение навыка очищает только автоматический выбор; ручной остаётся. Смена/удаление навыка и обновление каталога приводят выбор в согласованное состояние.
- Явное отключение автоматически выбранного сервера оставляет предупреждение о недоступной зависимости навыка. Не подключать его снова молча при обычном обновлении каталога.
- Проверить фокус во всех диалогах настроек/ресурсов и мобильном drawer: перевод внутрь при открытии, удержание Tab/Shift+Tab, Escape, возврат к инициатору; фон недоступен для взаимодействия. Следовать существующим компонентам без новой тяжёлой UI-библиотеки.
- Подсказки сделать читаемыми: ориентир 12–13 px, контраст обычного текста не ниже 4,5:1, заметный keyboard focus и достаточная область touch-действий, ориентир 44 px.

**Основные файлы:** `CapabilitySwitches.vue`, `App.vue`, `useMcp.ts`, компоненты диалогов настроек/ресурсов, `style.css`; MCP API только при необходимости метаданных.

**Приёмка.** Матрица выбора: без навыка, навык со связями, ручной+автоматический сервер, смена/выключение/удаление навыка, явное отключение зависимости, unavailable-сервер, reload. Ручной выбор не теряется, недоступные инструменты не предлагаются модели. Тесты `useMcp` и интеграции выбора дополняются; клавиатуру и контраст проверить в браузере, включая масштаб 200%.

## Этап 4. Состояние генерации, маршрутизация и контекст — P1 — реализован

**Проблема.** «Думаю…» не объясняет длительное ожидание. Промежуточный ответ может замениться после самопроверки без объяснения. Подсказка Auto не всегда соответствует фактическому маршруту. Резерв ответа в контексте виден только после раскрытия.

**Изменения.**

- Показать стадии «Ожидаю ответ модели», «Получаю ответ», «Выполняю инструмент …», «Проверяю ответ», «Завершено/Отменено/Ошибка» и прошедшее время. Не показывать выдуманный процент или ETA.
- Добавить согласованное событие стадии в общий протокол `AgentEvent`, декодер клиента и runtime. Таймер ожидания может быть локальным; начало самопроверки должно подтверждаться событием, а не угадываться по паузе.
- Во время самопроверки отметить ответ как предварительный. `text.reset` заменяет только предварительный ответ соответствующего запуска. Итоговое предупреждение о неполноте показывать один раз.
- В Auto различать «Автоматический выбор» до запуска и подтверждённую модель после маршрутизации. Для предварительного показа использовать серверный расчёт, если он необходим; не копировать правила маршрутизации во frontend.
- В сообщении показывать понятное имя модели, технический ID — в подробностях. В индикаторе контекста явно подписать использованный объём, окно, резерв ответа и остаток для входных данных, сохранив текущий расчёт.

**Основные файлы:** `packages/agent-core/src/types.ts`/`AgentRuntime.ts`, API-протокол при необходимости, web `api/client.ts`, `useChats.ts`, компоненты ответа/composer/context и `useContext.ts`.

**Приёмка.** Проверить ожидание без deltas, ответ потоком, инструмент, самопроверку с продолжением, отмену на каждой стадии и обрыв SSE. Этапы соответствуют реальному запуску, Stop доступен, после завершения таймер остановлен. Протокольные тесты проверяют новое событие и существующие события; runtime-тесты — ограничение продолжений и замену предварительного текста. Не раскрывать внутренние рассуждения модели.

## Этап 5. Ошибки инструментов и восстановление — P1, отдельный объём надёжности

**Проблема.** Ошибка `fetch` завершила ответ строкой `Tool execution failed.`; после reload осталась общая фраза «Запрос не завершён успешно.». Пользователь теряет причину и понятный следующий шаг.

**Изменения.**

- Ввести безопасные категории ошибок: отмена, timeout, недоступный provider/MCP, отказ инструмента, запрещённый/неизвестный инструмент, некорректный или слишком большой результат. Показывать локализованную причину и применимое действие; не выводить ключи, сырые исключения и конфиденциальные аргументы.
- Сохранять безопасный код/описание ошибки вместе с запуском, чтобы после reload состояние было эквивалентно живому. Использовать совместимое расширение хранения, старые записи читать с общей причиной.
- Отдельно определить восстанавливаемые ошибки вызова. Для них разрешить ограниченный возврат безопасного error-result модели, чтобы она могла объяснить ограничение или продолжить без инструмента. Отказ allowlist, нарушение формата/лимитов и ошибки инфраструктуры не превращать безусловно в успешный результат. Сохранить лимит цикла и отмену.
- Повтор запроса доступен только как явное действие пользователя с понятным предупреждением о повторном запуске. Не вводить автоматические повторы инструментов с побочными эффектами и не выдавать повтор за продолжение старого запуска.

**Основные файлы:** `AgentRuntime.ts`, типы ToolRegistry/событий в затронутых пакетах, API, storage run metadata, декодер истории и карточки ошибок web. Конкретную границу категорий уточнить по существующим интерфейсам перед редактированием.

**Приёмка.** Тестовая матрица включает безопасный отказ инструмента, timeout, отмену, неизвестный/запрещённый инструмент, невалидный/большой результат и ошибку provider. Ошибка одного чата не повреждает другой; секреты не попадают в события и БД. Reload сохраняет причину; восстанавливаемый случай даёт объяснение без зацикливания, остальные явно завершаются ошибкой. Этот этап не означает выполнение всего Phase 9.

**Реализовано.** События ошибок несут ограниченный `errorCode`; SQLite добавляет nullable `runs.error_code` с миграцией для старых баз, а старые запуски продолжают показывать общее сообщение. Интерфейс локализует причину и следующий шаг, карточка инструмента показывает фиксированный безопасный результат восстановления. Только инструмент, который явно пометил исключение `code: "unavailable", recoverable: true`, разрешает модели один проход без этого инструмента; сырое исключение не передаётся, повтор того же инструмента в запуске блокируется, общий лимит раундов остаётся в силе. Кнопка «Повторить запрос» требует подтверждения с предупреждением о возможных повторных внешних действиях. Автоматических повторов нет.

Проверки этапа 5: тесты рантайма — 72, storage — 16, web — 81; полный набор workspace — 270 тестов. `npm run typecheck`, `npm run lint` (0 ошибок, 603 существующих предупреждения формата) и `npm run build --workspace=@agenter/web` прошли. `git diff --check` прошёл. Браузерная проверка этапа недоступна по описанному выше ограничению автоматизации Chrome.

## Этап 6. Черновик и навигация во время генерации — P2

**Проблема.** Во время запуска блокируются история и подготовка следующего сообщения. Уже имеющееся сохранение черновиков по чатам не решает глобальную блокировку.

**Изменения.**

- Разрешить редактировать черновик и читать другой чат во время единственного активного запуска. Отправку второго сообщения блокировать до окончания/отмены; указать, где идёт генерация.
- Привязать поток, ответ, инструменты и Stop к исходному `chatId`/запуску независимо от открытого чата. Добавить компактный индикатор «Генерация в …» с возвратом и отменой.
- Сохранять существующий механизм черновиков/настроек по чатам. При возврате в активный чат показывать актуальный поток, не заменять его устаревшей загрузкой из БД.
- Не разрешать удаление чата с активным запуском до его окончания или явной отмены. Не менять ресурсы уже начатого запуска вслед за переключателями следующего сообщения.

**Основные файлы:** `App.vue`, `useChats.ts`, `Sidebar.vue`, `ChatView.vue` и composer. Изолировать состояние одного запуска минимальным способом; не строить менеджер параллельных запусков.

**Приёмка.** Начать ответ в A, открыть B, изменить черновик B, вернуться A, отменить, перезагрузить. Deltas/ошибки/инструменты остаются в A, черновик B сохранён, второй запрос не отправлен, Stop отменяет A. Покрыть гонку загрузки истории и SSE, финальное событие в другом открытом чате и сохранение настроек для будущего запроса.

**Реализовано.** `useChats` держит один активный запуск вместе с его `chatId` и исходным массивом сообщений. Историю можно переключать во время генерации; возврат к исходному чату показывает тот же поток, а терминальные события обновляют именно его даже при открытом другом чате. Открытый чат и настройки/черновик продолжают храниться по отдельному ключу. В другом чате поле и вложения доступны для подготовки, отправка блокируется глобально. Плашка показывает исходный чат, возвращает к нему и отменяет запуск. Удаление активного чата блокируется и в UI, и в composable.

Проверки этапа 6: web — 84 теста, включая A → B → A, Stop из B, финальное событие при открытом B, блокировку второго запроса и защиту активного чата от удаления; полный набор workspace — 273 теста. `npm run typecheck`, `npm run lint` (0 ошибок, 603 прежних предупреждения форматирования), web build и `git diff --check` прошли. Браузерная проверка этапа недоступна по ограничению автоматизации Chrome.

## Этап 7. Вставка текста и проверка файлов — P2

**Проблема.** Вставка текста длиннее 100 символов автоматически создаёт файл, но интерфейс не объясняет переход. Это утверждённое поведение от 2026-10-01, описанное в `docs/text-files.ru.md`, а не случайный дефект.

**Изменения.**

- Сохранить текущий порог и добавить краткое объяснение у карточки: «Длинный текст добавлен как файл».
- Добавить обратимое действие «Вставить в поле»: перенести содержимое с сохранением текста и переносов, удалить исходную карточку, не создавать дубликат; существующий черновик сохранить и вставлять в определённую позицию. При нарушении лимитов показать причину без потери данных.
- Изменение поведения по умолчанию рассматривать только как отдельно согласованное решение. Файл продолжает передаваться как справочные данные; действие переноса явно переводит текст в пользовательское сообщение.
- Проверить целый путь генерации HTML/Markdown → preview → скачивание → повторное открытие чата. Сохранить sandbox/CSP HTML и очистку Markdown. Ограничение браузерной автоматизации не считать подтверждённой ошибкой скачивания.

**Основные файлы:** `useTextAttachments.ts`, компоненты вложений/composer, `textFiles.ts`, `answerFiles.ts` только при обнаруженном дефекте; `docs/text-files.ru.md` обновить вместе с утверждённым поведением.

**Реализовано.** Карточка из буфера объясняет, что длинный текст добавлен как файл, и предлагает вставить его в позицию курсора. Вставка заменяет выделение, сохраняет остальной черновик и переносы, затем удаляет карточку. При превышении лимита карточка остаётся. Если длинный текст нельзя приложить из-за лимита размера/количества вложений, стандартная вставка в текстовое поле остаётся разрешена и сохраняет исходные данные. Скачивание из карточки предпросмотра использует MIME-тип HTML или Markdown. Повторное открытие истории восстанавливает ответные документы из сохранённого текста и формата.

Проверки этапа 7: web — 89 тестов, включая вставку по выделению, лимит черновика без потери карточки, fallback вставки из буфера, восстановление HTML/Markdown после открытия чата, sandbox/CSP и UTF-8 скачивание; полный набор workspace — 278 тестов. `npm run typecheck`, `npm run lint` (0 ошибок, 603 существующих предупреждения форматирования), web build и `git diff --check` прошли. Браузерный просмотр и физическое мобильное устройство в этой сессии проверить нельзя: локальная вкладка Chrome не переподключилась после тайм-аута; тесты Blob, MIME, восстановление и sandbox прошли автоматически.

**Приёмка.** Вставки 100/101 символ, многострочный текст, уже заполненное поле, несколько вложений, ограничения размера, отмена переноса. После переноса ровно одна копия текста. Для HTML и Markdown проверить preview и реальное скачивание в Chrome вручную, имя/содержимое файла и reload; существующие unit-тесты Blob оставить частью проверки. Отдельно проверить вставку и клавиатуру на физическом мобильном устройстве, если оно доступно; иначе отметить ограничение.
